# Самообучение суфлёра на моих чатах — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Суфлёр учится на реальных данных: что из предложенного я выбрал, что написал вместо этого сам и как на это ответила собеседница. Из этого собирается профиль моей манеры письма, который подмешивается в промпт, — варианты со временем звучат как я, а не как языковая модель.

**Чем это НЕ является:** дообучением весов модели. Веса DeepSeek мы не трогаем — это retrieval + обусловливание промпта: храним свои сообщения, выбираем релевантные, кладём в промпт как образцы и как статистику. Для настоящего файнтюна нужны тысячи примеров и другой API; на переписке одного человека он и не нужен — few-shot из собственных сообщений даёт почти весь эффект за копейки.

**Architecture:** Три слоя поверх текущего кода. **Сбор** — `store.py` (SQLite) пишет выданные подсказки, мои отправленные сообщения и исходы. **Осмысление** — `matching.py` определяет, взял я вариант, поправил или написал своё; `outcome.py` оценивает реакцию собеседницы. **Применение** — `profile.py` собирает из накопленного блок для промпта, `suggester` его подмешивает.

**Tech Stack:** то же, что в проекте, плюс стандартные `sqlite3` и `difflib`. Новых зависимостей нет.

## Global Constraints

- Новых внешних зависимостей не добавлять: `sqlite3` и `difflib` есть в stdlib.
- База `suflor.db` лежит рядом с `suflor.session`, в git не попадает (добавить в `.gitignore`).
- Бот по-прежнему **никогда** не пишет собеседникам. Обучение ничего не отправляет.
- Все новые чистые функции покрываются тестами; работа с БД тестируется на `tmp_path`.
- Пока данных мало (< `min_samples`), промпт должен собираться ровно как сейчас — никаких «полуобученных» блоков.
- Исходники в `src/suflor/`, тесты в `tests/`.

## Приватность — решить до Task 1

База хранит тексты переписок в открытом виде на диске: мои сообщения, её сообщения, время. Это заметно больше того, что проект хранит сейчас (сейчас — ничего, всё живёт в оперативке одного запроса). Прежде чем реализовывать:

- `.gitignore` обязан покрывать `*.db` — иначе личная переписка уедет в репозиторий.
- В конфиге предусмотрен выключатель `learning.enabled` и команда `/forget @user`, стирающая всё по конкретному человеку.
- Шифрование базы в план не заложено. Если ноутбук не под BitLocker, любой, у кого есть доступ к файлам, прочитает переписку. Скажи, если нужно шифровать, — тогда добавится зависимость (`sqlcipher`) и отдельная задача.

## Две ловушки, ради которых план устроен именно так

**1. Схлопывание стиля.** Если учить модель на вариантах, которые она сама и написала, она замкнётся на себе: свои обороты будут возвращаться усиленными, и через месяц все подсказки станут одинаковыми. Поэтому **корпус стиля — только то, что писал я сам**: сообщения без подсказки и мои правки предложенного (`own`, `edited`). Принятые без правок варианты (`variant`) в образцы стиля не идут никогда — они учитываются только в статистике «какой тон я выбираю».

**2. Ложное сопоставление.** Короткое «норм» совпадёт с вариантом случайно. Поэтому для текстов короче 15 символов — только точное совпадение, похожесть не считаем.

### Task 1: Хранилище (`store.py`)

**Files:**
- Create: `src/suflor/store.py`
- Test: `tests/test_store.py`
- Modify: `.gitignore`

**Interfaces:**
- Consumes: ничего.
- Produces:
  - `open_store(path: str) -> sqlite3.Connection` — открывает базу, создаёт схему, если её нет (идемпотентно).
  - `save_suggestion(conn, chat_id, tones, variants, incoming_text) -> int` — id записи.
  - `last_suggestion(conn, chat_id) -> dict | None` — последняя подсказка по чату (для сопоставления).
  - `save_sent(conn, chat_id, text, source, suggestion_id=None, variant_index=None) -> int`.
  - `save_outcome(conn, sent_id, replied_at, reply_text, delay_s, score)`.
  - `pending_outcomes(conn, chat_id) -> list[dict]` — отправленные, у которых исход ещё не записан.
  - `style_samples(conn, chat_id=None, limit=50) -> list[dict]` — мои сообщения (`own`/`edited`) от новых к старым.
  - `tone_stats(conn, chat_id=None) -> dict[str, int]` — сколько раз какой тон был выбран.
  - `forget_chat(conn, chat_id)` — удаляет всё по чату.

Схема (три таблицы, времена — UTC ISO-строками, как удобно sqlite):

```sql
CREATE TABLE IF NOT EXISTS suggestions (
    id INTEGER PRIMARY KEY,
    chat_id INTEGER NOT NULL,
    created_at TEXT NOT NULL,
    tones TEXT NOT NULL,           -- JSON-список тонов на момент выдачи
    variants TEXT NOT NULL,        -- JSON-список вариантов
    incoming_text TEXT             -- на что отвечали
);

CREATE TABLE IF NOT EXISTS sent (
    id INTEGER PRIMARY KEY,
    chat_id INTEGER NOT NULL,
    sent_at TEXT NOT NULL,
    text TEXT NOT NULL,
    source TEXT NOT NULL,          -- 'variant' | 'edited' | 'own'
    suggestion_id INTEGER,         -- NULL, если подсказки не было
    variant_index INTEGER          -- какой по счёту вариант, с нуля
);

CREATE TABLE IF NOT EXISTS outcomes (
    sent_id INTEGER PRIMARY KEY REFERENCES sent(id) ON DELETE CASCADE,
    replied_at TEXT,               -- NULL = не ответила в отведённое окно
    reply_text TEXT,
    delay_s INTEGER,
    score REAL NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_sent_chat ON sent(chat_id, sent_at);
```

**Interfaces:**
- Consumes: ничего (чистые функции).
- Produces:
  - `normalize(text: str) -> str` — нижний регистр, схлопнутые пробелы, снятая пунктуация и эмодзи. Для сравнения, не для хранения.
  - `classify_sent(text: str, variants: list[str]) -> tuple[str, int | None, float]` — `('variant'|'edited'|'own', индекс, похожесть)`.

Правила:
- нормализованное совпадение → `('variant', i, 1.0)`;
- `difflib.SequenceMatcher(None, norm_a, norm_b).ratio() >= 0.72` → `('edited', i, ratio)`;
- текст короче 15 символов и не совпал точно → `('own', None, 0.0)`, похожесть не считаем вовсе;
- иначе `('own', None, 0.0)`.

### Task 3: Оценка реакции (`outcome.py`)

**Files:**
- Create: `src/suflor/outcome.py`
- Test: `tests/test_outcome.py`

**Interfaces:**
- Consumes: ничего (чистые функции).
- Produces:
  - `score_reply(delay_s: int | None, reply_len: int, has_question: bool, median_delay_s: float, median_len: float) -> float` — 0.0–1.0.
  - `reply_stats(history: list[dict]) -> tuple[float, float]` — медианные задержка и длина её ответов в этом диалоге (база для сравнения).

Формула — намеренно простая и объяснимая:

| Условие | Вклад |
|---|---|
| ответа не было в окне `outcome_window_hours` (`delay_s is None`) | итог `0.0` |
| ответ есть | база `0.5` |
| ответила быстрее своей медианы | `+0.2` |
| ответ длиннее её медианы | `+0.2` |
| в ответе есть встречный вопрос | `+0.1` |

Это эвристика, а не истина: быстрый короткий ответ может значить и интерес, и отписку. Она нужна только чтобы ранжировать мои же удачные сообщения, поэтому ошибка в отдельном случае не критична. Сравнение идёт с медианой **этой** собеседницы, а не с абсолютными числами, — у разных людей разный темп.

### Task 4: Сбор сигналов в рантайме (`main.py`)

**Files:**
- Modify: `src/suflor/main.py`
- Test: `tests/test_main.py`

**Interfaces:**
- Consumes: `store`, `matching`, `outcome`.
- Produces: три новых места записи в существующем обработчике.

Что происходит по событиям:

1. **Выдали подсказку** (обе ветки — входящее и `/hint`) → `save_suggestion(...)`, id держим в памяти `PENDING[chat_id]`, а также в базе как «последняя по чату».
2. **Моё исходящее в обычном чате** (не в пульте) → берём `last_suggestion(chat_id)`, если она свежая (не старше `match_window_minutes`, по умолчанию 60), зовём `classify_sent` → `save_sent(...)`. Если подсказки не было или она протухла — пишем `source='own'`: это всё равно образец моей манеры, и именно такие образцы ценнее всего.
3. **Входящее от неё** → перед генерацией подсказки закрываем висящие исходы: для каждой строки из `pending_outcomes(chat_id)` считаем задержку и `score_reply`, пишем `save_outcome`. Плюс тем же проходом закрываем нулём всё, что старше окна, — ответа уже не будет.

Ключевая деталь: сейчас `handler` выходит из ветки команд пульта через `return` и дальше фильтруется `should_suggest`, который режет исходящие. Запись отправленного должна стоять **до** этого фильтра и явно исключать `chat_id == panel_id`, иначе мои же команды `/on`, `/hint` попадут в корпус стиля.

### Task 5: Профиль манеры (`profile.py`)

**Files:**
- Create: `src/suflor/profile.py`
- Test: `tests/test_profile.py`

**Interfaces:**
- Consumes: `store`.
- Produces: `style_block(conn, chat_id, tones, cfg) -> str` — готовый кусок промпта или `""`, если данных мало.

Что попадает в блок:

- **Образцы.** До 8 моих сообщений (`own` и `edited`, никогда `variant`): сначала до 5 из этого же чата — с конкретным человеком у меня свой тон, — остальное добираем из общего корпуса. Внутри каждой группы сортировка по `score` убывающе, при равенстве — свежие вперёд. Пока сообщений меньше `min_samples` (5), возвращаем `""`.
- **Предпочтения по тонам.** Из `tone_stats`: «чаще всего ты берёшь вариант „лёгкий, с юмором“ (11 из 18), „игривый“ — ни разу». Тон, который я не выбрал ни разу за 20 подсказок, помечается отдельно.
- **Как я правлю предложенное.** Считается по парам (`variant`, что реально отправлено) для `source='edited'`: медианная разница в длине и в числе эмодзи. Если я стабильно режу длину — в блок идёт «я обычно короче предложенного примерно на треть»; если стабильно убираю смайлы — «смайлов ставлю меньше». Правило попадает в блок только при 5+ правках в ту же сторону, иначе это шум.

Формат блока (идёт в system-часть, после стиля из конфига):

```
Вот как я пишу сам — держись этой манеры, это важнее любых общих правил:
- «норм, отдыхаю. кофе пью на балконе»
- «да ладно, серьёзно?) и как оно?»
- «сегодня никак, давай в четверг»
Чаще всего я беру вариант в тоне «лёгкий, с юмором» (11 из 18), «игривый» — ни разу.
Предложенное я обычно сокращаю примерно на треть и ставлю меньше смайлов.
```

## Что осознанно оставлено за рамками

- **Style card** — сжатая выжимка манеры, которую пишет сама модель раз в N новых образцов и которая кладётся в промпт вместо восьми примеров. Дешевле по токенам на длинной дистанции, но требует кэша и инвалидации. Смысл имеет, когда корпус перевалит за пару сотен сообщений.
- **Эмбеддинги для подбора образцов** под конкретную ситуацию (похожий момент в диалоге → похожий мой ответ). Заметно точнее, чем «свежие с высоким score», но тянет за собой векторную модель и индекс.
- **A/B тонов**: намеренно чаще предлагать редко выбираемый тон, чтобы проверить, дело в тоне или в формулировках. Статистики одного человека на это, скорее всего, не хватит.
